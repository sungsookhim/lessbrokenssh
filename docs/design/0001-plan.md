0001 implementation plan: Unicode rendering
============================================

How we build [0001-unicode-rendering.md](0001-unicode-rendering.md), in order. Each step leaves a working app that can be tried on real hardware.

**Test machines:** LC 475 (68LC040, `68040` build) and iMac G3 (`g3` build). The LC II comes later; it should behave like the LC 475, only slower.

## Changes from the design doc

**All atlas glyphs are made on the build host and hand-tuned, including box, block and Braille characters.** The design doc had box/block/Braille glyphs drawn by code on the Mac at startup. Instead, every glyph is:

1. **drawn large:** box/block/Braille/shade glyphs are drawn by a script, and symbols are rendered from a font, at 8× the cell size (48×96 for a 6×12 cell);
2. **scaled down** to the cell size by area averaging, then thresholded to 1 bit;
3. **saved as editable text art**, one file per glyph per cell size, which we then hand-edit so each glyph keeps the character's intent at 6 px wide. Braille is the main case: at 6×12 the 2×4 dots need hand placement to stay distinct.

The tools never overwrite a glyph file that has been hand-edited (see Glyph files). The Mac side becomes simpler: it only looks glyphs up and copies them to the screen, with no drawing code per character type. The cost is that we only support the cell sizes we've made glyph sets for. That's fine: Monaco 9 at 512/640 wide, and the iMac's font at one or two sizes.

## Glyph files

```
glyphs/
  6x12/
    2500.txt        box drawing ─
    2580.txt        upper half block ▀
    2801.txt        Braille dot 1
    23FA.txt        ⏺ (exported from a font)
    ...
  8x16/
    ...
  sources.tsv       code point → where the glyph came from (procedural / font name), edited flag
```

A glyph file is plain text, one row per pixel line, `#` for ink and `.` for paper. A header line records where it came from:

```
# U+2580 UPPER HALF BLOCK  source=procedural  edited=no
######
######
######
######
######
######
......
......
......
......
......
......
```

- **Editing:** text art diffs cleanly in git and needs no special editor.
- **Hand edits are protected:** when someone edits a file by hand, they set `edited=yes`, and the generators skip it unless run with `--force`.
- **Preview:** `preview.py` renders each set to a PNG contact sheet. It shows each glyph at 8× zoom with its cell grid, the large source it was scaled from, and the glyphs in context (a sample Claude CLI frame, a btop graph), so you can judge the result without a Mac.

## Steps

### Step 0: diagnostics

At startup, print one line to the terminal window with the screen size and depth, the cell size and font, and whether Color QuickDraw, the Text Encoding Converter and any CJK script systems are present. For example:

```
lessbrokenssh: screen 640x480 8-bit, cell 6x12 (Monaco 9), TEC no, scripts: none
```

This tells us the real cell sizes on the LC 475 and the G3 before we draw a single glyph.

### Step 1: layout and color correctness (design milestone 1, Mac side)

- **One helper per cell:** both drawing loops get the character for a cell from a single helper instead of each doing its own Unicode mapping.
- **Continuation cells** (the right half of a wide character) draw as blank, so a wide character takes 2 cells: `◊` plus a blank, instead of `◊◊`.
- **Color reads:** check the color type before reading it. Indexed colors 16–255 and RGB colors map to the nearest of the 8 QuickDraw colors. (Today indexes above 15 read past the end of a 16-entry table.)
- **Invisible text:** if the foreground color maps to the same QuickDraw color as the background, use the default foreground instead. For example, the Claude CLI's grey secondary text would otherwise turn white on white.
- **Test pattern:** add `tests/unicode-sample.txt` with every character class and ruler lines, to `cat` over SSH.

**Check on hardware:** `cat tests/unicode-sample.txt`, then run the Claude CLI. The columns should line up, even though special characters still show as `◊`.

### Step 2: width table (design milestone 1, libvterm side)

- Fork `cy384/libvterm` to `sungsookhim/libvterm` and point `.gitmodules` at the fork, on a `lessbrokenssh` branch.
- Add `tools/unicode/gen_fullwidth.py`, which regenerates `src/fullwidth.inc` from the Unicode 16 `EastAsianWidth.txt` and `emoji-data.txt`.
- Widen a cell to 2 when U+FE0F follows a narrow character that has emoji presentation.

**Check:** the emoji and `⚠️` lines in the test pattern line up. The Claude CLI's lines with emoji no longer shift.

### Step 3: glyph tools (host only)

- Add Python 3 with Pillow and fontTools to the `Containerfile`, and a `./build.sh glyphs` target.
- `tools/glyphs/procedural.py`: draws box (light, heavy, double, rounded), block, quadrant, shade, Braille, sextant and Powerline glyphs at 8×, then scales them down into `glyphs/<size>/`.
- `tools/glyphs/export_font.py`: renders code points from `symbols.txt` out of a font (BDF pixel fonts directly; TTF at 8× then scaled down).
- `tools/glyphs/preview.py`: the contact sheet.
- `tools/glyphs/pack.py`: turns `glyphs/<size>/*.txt` into
  - `glyphs.r`: one `'GLYF'` resource per cell size, holding a 1-bit strip of all glyphs, included from `ssheven.r`;
  - `glyph-table.h`: the sorted code point → glyph index table.
- Make the first 6×12 set (box, block, Braille, shade), hand-tune it from the preview, and commit it.

### Step 4: drawing from the atlas (design milestone 2)

- **New file `ssheven-glyph.c`:** at startup and on font size change, load the `'GLYF'` set matching the cell size into a 1-bit `BitMap`, and look up code points in `glyph-table.h` (binary search with a small cache in front).
- **Drawing loops:** a cell with a glyph ends the current text run and is drawn with `CopyBits` (`srcCopy`, colored by the port's foreground and background colors). Neighbouring glyph cells with the same colors share one color setup.
- **Timing:** time full redraws with `TickCount()` into the debug window, before and after, on a captured Claude CLI screen. On the LC 475, the goal is to stay within 20% of step 1.

**Check:** the Claude CLI's frame and logo and btop's graphs draw correctly on both machines.

### Step 5: symbols and capture

- `tools/unicode/capture.py`: records the non-ASCII code points from a `script` log of a real session, and lists the ones that have no glyph yet.
- Export and hand-tune the Claude CLI and btop symbol list at 6×12, then make the 8×16 set for the G3.

### Step 6: emoji (design milestone 4)

- Switch the terminal window from `NewWindow` to `NewCWindow`, so color bitmaps draw with full color in any mode.
- `tools/glyphs/export_emoji.py`: takes Twemoji PNGs and makes 8-bit, 4-bit and mono variants plus a mask, quantized to the Mac system palettes, as `'EMOJ'` resources.
- Pick the variant from the screen depth at startup, and draw with `CopyMask`.

### Step 7: iMac fonts and CJK (design milestone 5)

- Embed a TrueType subset as the 8×16 base font.
- If the Text Encoding Converter and a CJK script system are present, draw CJK through them; otherwise use the replacement glyphs.
- Try ATSUI as an alternative and time it.

### Step 8: Unicode copy and paste (design milestone 6)

Selection and copy read all of `chars[]`, encode to UTF-8, and convert to Mac Roman for the clipboard (or keep Unicode on the G3 through TEC).

## Getting builds onto the Macs

`dist/ssheven-68040.bin` and `dist/ssheven-g3.bin` are MacBinary files. They keep the resource fork when copied over the network or on a FAT-formatted disk, and get unpacked on the Mac with StuffIt Expander or MacBinary II+. The `.dsk` files are HFS disk images for emulators or for writing to a floppy or Zip disk. How the files actually get to the LC 475 and G3 is decided when we first test.
